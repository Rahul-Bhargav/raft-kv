3 · Key idea: one algorithm core, two ways to run it

Can the code the tests verify be the same code the panel watches in Docker? Yes, if the Raft logic never does its own I/O.

  • Time is ticks. I/O is messages in and messages out. Durability goes through a Storage interface.
  • Tests drive the node with a fake clock and network, so any run reproduces from its seed and a thousand fault schedules run in about 13 seconds.
  • The demo drives the same class with a 100 ms timer and HTTP. What the panel watches is the code the tests verified.
  • This is the same split etcd's Raft library uses: the library implements the algorithm, and the caller does network and disk I/O.

4 · The Raft core raft/

This is the part to own line by line. Everything else exists to drive it or to show what it's doing.

class Role(str, Enum): FOLLOWER = "follower"; CANDIDATE = "candidate"; LEADER = "leader"

@dataclass(frozen=True)
class RaftConfig:
    heartbeat_interval: int = 10      # ticks
    election_timeout_min: int = 30    # ticks; actual timeout is random in [min, max)
    election_timeout_max: int = 60
    max_entries_per_append: int | None = None   # cap per AppendEntries; None = unlimited

class RaftNode:
    def __init__(self, node_id: str, peers: list[str], storage: Storage,
                 rng: random.Random, config: RaftConfig = RaftConfig()): ...

    # inputs
    def tick(self) -> None                                      # advance logical time by one tick
    def receive(self, msg: Message) -> None                     # handle one incoming Raft message
    def propose(self, command: dict) -> tuple[int, int] | None  # (index, term) if leader, else None

    # outputs (each returns the queued items and clears them)
    def take_messages(self) -> list[Message]                    # messages to send
    def take_committed(self) -> list[tuple[int, Entry]]         # (index, entry), in log order
    def take_events(self) -> list[str]                          # e.g. "became leader (term 4)"

    # read-only state
    node_id, peers, role, term, voted_for, leader_id, commit_index, last_applied, storage

At 100 ms per tick that's a heartbeat every 1 s and elections after 3–6 s, slow enough to watch. The tests use the same numbers, since ticks cost nothing there. RaftConfig is frozen because its default instance is shared by every node.

peers lists the other nodes, not the node itself. A majority is (len(peers) + 1) // 2 + 1, which is 3 of 5. Only term, voted_for and the log live in storage and survive a restart. The role, commit index, last_applied, next_index, match_index and the timers are rebuilt from scratch.

How take_messages(), take_committed() and take_events() work

The node never sends anything or applies anything itself. While it handles an input, it only writes down what should happen next, in three places:

  • An outbox: a list of messages it wants to send, such as a vote reply or heartbeats.
  • Committed-but-not-applied entries: everything between last_applied + 1 and commit_index.
  • Events: short strings such as became leader (term 4), for the dashboard's event feed and for the safety checks.

"Take" means hand over once.

  • take_messages() returns the outbox and empties it.
  • take_committed() returns the newly committed entries as (index, entry) pairs in log order and moves last_applied forward, so each entry is handed out exactly once.
  • take_events() returns the queued events and empties the list.

Example: a follower receives an AppendEntries carrying entry 7, with leader_commit = 7. It appends and saves the entry, queues a "success" reply, and moves its commit index from 6 to 7. Then take_messages() returns [reply to leader] and take_committed() returns [(7, entry 7)].

Can multiple threads interfere with these steps?

No, because no threads touch the node. The simulator is a plain loop. The demo server runs a single asyncio event loop, which is one thread. Asyncio only switches between tasks at an await. The node's methods are ordinary functions with no await inside. So calling the node and collecting its outputs always runs start to finish, with nothing in between.

All three entry points (the POST /raft handler, the tick loop and POST /client/write) go through one helper. This is the server's helper in server/node_server.py, shortened. The simulator has its own: SimCluster._collect.

def step(self, call, *args):
    result = call(*args)                     # node.receive / tick / propose: plain function, no await
    for msg in self.node.take_messages():
        if msg.dst not in self.blocked:      # the partition filter
            asyncio.create_task(self.send(msg))  # sends run later as their own tasks and never touch the node
    for _index, entry in self.node.take_committed():
        self.kv.apply(entry.command)         # update the KV store
    for event in self.node.take_events():
        self.events.append({"time": time.time(), "event": event})  # stamped with wall-clock time
    del self.events[:-MAX_EVENTS]            # keep the last 20
    return result

# for example, inside the POST /raft handler:
self.step(self.node.receive, msg)

There's one rule: never put an await between calling the node and collecting its outputs. With one helper, that rule lives in one place. This is also why the design uses asyncio. A threaded web server would need a lock around the node.

Outbox or callbacks? decided: outbox (Q10)

A · Outboxchosen
self._outbox.append(reply)   # inside the node
# the driver collects it after the call returns
  • ✅ Messages can't leave before the handler has finished saving term, vote and log. R1 is guaranteed by the structure.
  • ✅ The node holds no reference to the network. A unit test calls receive() and inspects take_messages().
  • ➖ A few extra lines in the node, plus the collecting step in each driver (SimCluster._collect in the simulator, step() in the server).
B · Callbacksnot chosen
RaftNode(..., send=transport.send, apply=kv.apply)
self.send(reply)            # inside the node
  • ✅ Reads exactly like the paper.
  • ➖ R1 becomes a habit, not a guarantee. Every handler must save before calling send(), which is easy to break in a later edit, by you or an AI.
  • ➖ It doesn't remove the one-thread requirement. The same rule about await applies.

Decision: the outbox. The two are about the same size, and the outbox turns R1 from a rule we have to remember into one we can't break. The code follows it: RaftNode never touches a network, and every driver collects the outputs after each call.

These two together are the consistency check. The follower accepts the entries only if its own entry at prev_log_index has term prev_log_term. If it doesn't, it replies with failure and the leader retries starting further back. This is what keeps every log identical."Does your entry 6 have term 4?"
entriesThe new entries, each with the term it was created in and the command. There's no index field: an entry's position is prev_log_index + 1, then + 2, and so on. An empty list is a plain heartbeat. Heartbeats carry any entries the follower hasn't confirmed yet.One entry, which becomes #7: set z = 7, created in term 4
leader_commitThe highest index the leader knows is committed. The follower moves its own commit index up to min(leader_commit, index of its last new entry), which is how followers find out what's safe to apply.Entries 1–6 are committed. 7 isn't yet, since it was just sent.

Replies describe themselves. Messages are one-way (Q4), so the leader can't look up "which request was this a reply to?" Each reply carries everything needed to handle it, in any order: success, match_index (the last index the request covered, or 0 on failure) and last_log_index (the follower's last index, which tells the leader where to retry after a failed check). The leader ignores stale replies: ones with a lower term, or a match_index below what it already knows.

R6The leader commits by counting replicas only for entries from its own term.test_figure8
R7A new leader appends a no-op entry in its term, so entries from earlier terms get committed without waiting for a client write.test_new_leader_commits_previous_entries

Decided during implementation

The spec left these open or turned out incomplete. Each was settled while the code was written and is recorded in the task notes in PLAN.md.

  1. Strict R4: seeing a higher term does not reset the election timer. R4 lists only three resets: a valid AppendEntries from the current leader, granting a vote, and starting an election. Adopting a newer term is not one of them. Why: a candidate with an outdated log can never win, but if its messages reset every timer, nobody who could win would ever stand. A leader's timer is paused, because leaders never time out. A leader that steps down resumes the countdown it was elected with. Both have unit tests.
  2. Every heartbeat resends all unconfirmed entries. next_index moves only when a follower confirms entries, so every AppendEntries, heartbeats included, carries everything from next_index on. A lost message is retried by the next heartbeat, so there is no separate retry path. The cost is resending the same entries every 10 ticks until they are confirmed, which is fine at this size. A failure reply carries match_index 0, so the rule "ignore a lower match_index" also drops a late failure once the follower has confirmed something.
  3. An optional batch cap, max_entries_per_append, and the finding behind it. None means no limit (today's default), and below 1 raises ValueError. The cap only limits message size: a success reply doesn't send the next batch, the next heartbeat or proposal does. Why: with unlimited batches and the R7 noop, every reply in a leader's term also covers the leader's noop, so R6's term check never changes an outcome at the cluster level, and a Figure 8 test could not fail. With a cap of 1, a follower can confirm an old-term entry before the noop arrives, which is the case R6 guards against. This was the T13 decision, option A (§14).
  4. Storage bounds. MemoryStorage raises IndexError for an index outside the log: term_at outside 0..last, entry_at outside 1..last, and entries_from or truncate_from below 1. Past the end is a harmless no-op. So the node checks prev_log_index <= last_index() before it calls term_at(prev_log_index).
  5. Two deliberate asserts. An AppendEntries from the current term that reaches a leader means two leaders in one term, and the node stops with "two leaders in term N". A follower also asserts that it never deletes an entry at or below its commit index ("deleting committed"). Correct Raft does neither, so these can only fire on a bug, and then they stop loudly instead of letting nodes quietly disagree. Both show up in the evidence table in §9.

State machine

Commands are {"op": "set", key, value}, {"op": "delete", key} and {"op": "noop"}. Every node applies them in log order. After a restart, the KV store is rebuilt by re-applying committed entries from index 1, since there are no snapshots. The log starts at index 1; index 0 is a placeholder entry with term 0.

5 · The simulator sim/

SimNetwork (T05), SimCluster (T08), write (T11) and the time_out() helper (T12) are approved. It runs a whole cluster on a fake clock and a fake network, so a run is fast and always reproducible from its seed. Every cluster test in §9 uses it.

SimNetwork(rng, min_delay=1, max_delay=3, drop_rate=0, dup_rate=0)

  • Each message gets its own random delay in [min_delay, max_delay] ticks, both ends included, so messages arrive out of order without extra work. Messages due on the same tick come out in the order they were sent.
  • Random drop and duplicate rates. A duplicate is a second copy with its own delay.
  • partition(groups): nodes in different groups can't talk. Nodes you don't list form one more group together, so partition([{"n1"}]) isolates n1. A node named in two groups raises ValueError. A new partition() replaces the old one, and heal() removes it.
  • Partitions are checked when a message is due, not when it is sent (figure below). A message that is blocked then is gone for good: healing later does not bring it back.
  • All randomness comes from the rng passed in, so the same seed gives the same deliveries.

SimCluster(n=5, seed=0, config, **network_kwargs)

  • One seed fixes everything. A single random.Random(seed) drives the network, and each node gets its own Random seeded from it. Election timeouts stay independent of the network's draws, but are still set by the cluster seed.
  • step() is the figure above. A message to a crashed node is lost. run(ticks), run_until(cond, max_ticks) and leader() (the live leader with the highest term) are the helpers around it.
  • crash(id) throws away the node object but keeps its MemoryStorage, which plays the role of the disk. restart(id) rebuilds the node from that storage with fresh volatile state and an empty KVStore, which refills as committed entries are applied again.
  • partition(*groups) and heal() pass through to the network.
  • time_out(id) makes one node's election timer run out now: it ticks that node alone until it starts an election. Scripted tests set 1000-tick election timeouts so that nobody stands by accident, then pick who stands.

write(key, value, max_ticks=1000) and what "acknowledged" means

It writes through the current leader, as a client would: propose on the leader, then run until that same node has applied the entry's index. It returns True only if the entry applied there has the term it was proposed in. That is the simulator's version of the server's 200, and it is what the tests call an acknowledged write.

  • No leader: False at once.
  • A later leader overwrote the entry: False (the server answers 504).
  • Not applied within max_ticks: False (also 504). The entry may still be applied later.

checked_cluster() (tests/safety_checks.py)

A SimCluster with a SafetyChecker placed first in cluster.checkers. Every cluster test builds its cluster this way, so all five safety properties (§9) are checked after every step of every scripted and fuzzed run.

The checker only reads the cluster. It never sends, changes state or draws a random number, so a run is identical with or without it. A broken property raises SafetyViolation.

A partition is checked at delivery time

Only the moment a message is due matters: that is when the sender's group and the receiver's group are compared. The tests test_partition_is_checked_at_delivery_time and test_heal_restores_delivery_but_dropped_messages_stay_dropped pin it down.

6 · The node runtime server/

Built and approved at Gate 5: server/node_server.py (143 lines, 4 tests) and server/file_storage.py (41 lines, 2 tests). One NodeServer wraps one RaftNode in an aiohttp app.

  • Every call into RaftNode happens on the one event loop, so no locks are needed.
  • Every call into the node goes through one step() helper. After the call it sends take_messages() over HTTP (fire-and-forget, 500 ms timeout, errors ignored, since Raft already tolerates lost messages), applies take_committed() to the KV store, and keeps the last 20 take_events(), each with a wall-clock time.
  • Client writes: /client/write proposes on the leader, then checks once per tick, for up to 5 s, whether that index has been applied. It is a plain polling loop, with no futures.
  • Partition filter: each node keeps a set of blocked peers and drops messages going to or coming from them. Control endpoints (/state, /admin, /client) aren't filtered.
  • Storage: in memory for tests, one file for the demo: <data_dir>/<node_id>.json. See below.

Storage: a file in the demo, memory in tests decided

Tests: no file

MemoryStorage is a plain Python object. When the simulator "crashes" a node, it throws the node away but keeps this object, just as a real disk would survive. It's fast, and no files are involved.

Docker demo: yes, one file

Killing a container wipes its memory. Without a file, a restarted node comes back with term 0, no record of its vote, and an empty log.

What goes wrong if the demo has no file:

  1. It can vote twice in the same term. It forgets it already voted, so two candidates can both win the same term and you get two leaders (breaks Election Safety).
  2. It forgets entries it acknowledged. The leader counted that acknowledgement toward a majority. If enough nodes forget, a committed write disappears.

This is rule R1, and "what happens when a node restarts?" is very likely a panel question. With one crash at a time the demo would probably look fine, but it wouldn't be correct Raft.

Kept simple, as you asked: one file and an fsync on every change. FileStorage extends MemoryStorage and calls this after each of its three changing methods:

def _save(self) -> None:              # called on every change to term, vote or log
    log = [asdict(e) for e in self._log[1:]]   # without the index-0 placeholder
    with open(self._path + ".tmp", "w") as f:
        json.dump({"term": self._term, "voted_for": self._voted_for, "log": log}, f)
        f.flush()
        os.fsync(f.fileno())             # on disk before we return
    os.replace(self._path + ".tmp", self._path)   # swap in: the file is always old or new, never half-written
One concern, so I kept two extra lines: if we write straight over the node's file and it is killed mid-write, it's left with half a JSON file and can't start again. Writing to a temp file and swapping it in costs two lines and removes that problem. Everything else (append-only logs, directory fsync, checksums) is left out on purpose.

Side note for the panel: a killed container's writes are already in the operating system's cache, so in this demo fsync only matters if the whole machine loses power. We do it anyway because it's one line and it's what Raft requires.

How a client write works (3-node example)

The leader replies only after the entry is applied. If index 7 is applied with the same term, the client gets 200. If a different term is applied there (the entry was overwritten), or nothing is applied within 5 s, it gets 504. Losing leadership alone decides nothing: the new leader may still commit the entry, so the node keeps polling. A client never sees "ok" for a write that could still be lost.

7 · Docker setup and dashboard

docker-compose.yml

  • One image (python:3.12-slim + aiohttp) for all 6 containers. Only the start command differs.
  • node1–node5: fixed container names on host ports 8001–8005, with NODE_ID and PEERS set as environment variables (TICK_MS defaults to 100). Each has its own named volume at /data, and restart: "no" so a killed node stays down until you start it.
  • dashboard: port 8080. It reaches the nodes only over HTTP.
  • docker compose down -v wipes all state between demo runs.

Dashboard API

  • GET /api/cluster: sends GET /state to every node (300 ms timeout). No answer means the node is down.
  • POST /api/write: sends to the leader with the highest term and retries once on a 421. It always answers 200 with {node, status, body}, where status is the node's own answer (the dashboard answers for itself when no node is leader).
  • POST /api/partition: takes {groups} and works out each node's blocked set.
  • POST /api/heal
  • No kill or start endpoints: nodes are killed and started from a terminal (docker compose kill node3 / docker compose start node3).

8 · Demo scenarios

Kill and start nodes from a terminal. Writes and partitions are buttons on the dashboard.

1 · The leader fails

  1. Kill the leader: docker compose kill node3 (whichever node is leader).
  2. A new leader appears in a few seconds, at a higher term.
  3. Later, start the old one: docker compose start node3. It rejoins as a follower and catches up.

point out the term number goes up, and committed entries survived.

2 · A follower fails and catches up

  1. Kill a follower.
  2. Write a few values. They commit with 4 of 5 nodes.
  3. Start it. Its log fills in from the leader.

point out the node kept its term and log on disk, and the leader works backwards to find where their logs match.

3 · Partition with the leader in the minority strongest

  1. Click Leader + 1 | rest and write a value straight away.
  2. That first write goes to the cut-off leader: its entry stays dashed and the write times out.
  3. Wait a few seconds. The other side elects a leader at a higher term (two cards say LEADER, and the term tells them apart). Write again: the second write commits.
  4. Click Heal. The old leader steps down and its entry is replaced.

point out there are never two leaders making progress at once, and only uncommitted entries are ever lost.

4 · No majority

  1. Kill three nodes.
  2. With two nodes left there is no leader and no writes. The term keeps climbing as they keep running elections.
  3. Start one node. With three, a leader is elected and progress returns.

point out Raft gives up availability to stay consistent. The climbing term leads into a discussion of pre-vote.

9 · Tests

The tests are the evidence of correctness. The demo only illustrates. Every test runs in-process (on the simulator, on a single node, or on one small component), so none of them need Docker. 1,117 tests pass in about 13 seconds (uv run pytest).

Tests of "something good eventually happens" (a leader is elected, a follower catches up) need a time limit in ticks, or a broken implementation would hang the test. Those constants are called deadlines (*_DEADLINE). Each is about twice the slowest case measured, so changing the timeouts means measuring again. After the scope cut (§14) the suite was trimmed from 3,403 to 2,176 lines and from 1,249 to 1,117 tests: case matrices, variants of the same behavior, single-node tests the cluster tests already cover, and tests of helpers went. Every named rule test, the scenario tests, the safety checks and the fuzz test stayed.

The five safety properties (tests/safety_checks.py, checked after every simulator step)

The first four are Raft's own safety properties, with the names the paper gives them in its Figure 3. The fifth is ours. A SafetyChecker checks all five after every step of every cluster test, and breaking one raises a SafetyViolation that names the property, the tick, the nodes and the index or term involved.

Safety propertyWhat the check does
Election SafetyAt most one leader per term, ever. It records term → leader for the whole run, from both the "became leader" events and the nodes' roles, so a leader that lasted less than one step is still caught.
Log MatchingIf two logs have the same (index, term), they are identical up to that index. It checks each new or changed entry against every entry ever seen at that (index, term): same command, and the entry before it has the same term. By induction that is the same statement, and it works across the whole run, not just between logs that exist at the same moment.
Leader CompletenessEvery committed entry is in the log of every later-term leader. Each new leader is checked against the entries committed in earlier terms. An entry's commit term is the term of the first node seen with it committed, never earlier than the real commit term, so a stale leader legitimately elected in an older term isn't flagged.
State Machine SafetyNo two nodes apply different entries at the same index. It remembers what each node applied across crashes and restarts, so a node is also compared with itself from before its restart. A node that deletes or replaces an entry it has committed is reported here too.
No lost acknowledged writesAn acknowledged write (§5) stays applied on every node that has caught up that far, unless a later write sets the same key. It is checked against the checker's own replay of what each node applied, in a plain dict, so it checks the nodes' KV stores independently.

An example failure message

State Machine Safety violated at tick 91:
n1 applied index 2 from term 3 = {'op': 'noop'},
but n1 (before restarting) applied index 2
from term 2 = {'op': 'noop'} at tick 49

This is the Figure 8 damage, caught from the node's own history.

Why the checks keep a history

With R6 removed, the end state of the Figure 8 test still looks fine: every node ends with the same entries. Yet n1 had applied index 2 from term 2 before it crashed, and from term 3 after. A check that only compares the live nodes' current state passes all 10 seeds. The history-keeping checker fails all 10.

The fuzz test (tests/test_fuzz.py)

Each seed is one run of a 5-node cluster with randomized faults. The same seed always gives the same run, and a failure prints the seed and the command that reruns just that seed. FUZZ_SEEDS sets the number of seeds (default 1,000).

What each seed randomizes

  • The network: longest delay 2–8 ticks, 0–20% dropped, 0–30% duplicated.
  • The batch cap: none, 1 or 2 entries per AppendEntries.
  • Crashes (never more than 2 of 5 down, the leader half the time) and restarts.
  • Reboots: a node crashes and restarts in the same tick.
  • Partitions (often cutting off the leader) and heals.
  • Strikes: none, half or all new leaders are crashed or cut off 1–15 ticks after they win.
  • Client writes through SimCluster.write, each to a new key. Faults keep happening while a write waits, so writes get lost, overwritten and recovered in every way the faults allow.

Settling gets 1,200 ticks (SETTLE_DEADLINE): about twice the worst case (604 ticks) over seeds 0–9,999.

Why strikes and reboots were added

The first version used plain random faults, and it was too weak. Measured against a known bug over 8,000 seeds:

Known bugPlain faultsWith the new fault
R6 removed155 (strikes)
Vote lost on restart4109 (reboots)
  • Strikes: Figure 8 needs a leader lost in a window of a few ticks, after it has copied an older term's entry to a majority and before its own entry gets there. Random crashes rarely land in that window. A new leader is fragile, so striking it soon after it wins does.
  • Reboots: a node that crashes and is back in the same tick returns while the election is still running, which is when a forgotten vote can be used a second time.

Both are generic faults, not aimed at one bug. test_schedules_are_not_trivial also requires that 20 seeds really crash, reboot, partition, strike and acknowledge writes, at least half as often as measured.

Evidence that the checks catch real bugs

Each bug below was put into a scratch copy of raft/node.py on purpose, and the fuzz test was run over seeds 0–7,999 with its own random batch cap. A test suite that never fails proves nothing, so the question is how many seeds catch each bug, and which safety property fires.
