3 · Key idea: one algorithm core, two ways to run it

Can the code the tests verify be the same code the panel watches in Docker? Yes, if the Raft logic never does its own I/O.

  • Time is ticks. I/O is messages in and messages out. Durability goes through a Storage interface.
  • Tests drive the node with a fake clock and network, so any run reproduces from its seed and thousands of fault schedules run in seconds.
  • The demo drives the same class with a 100 ms timer and HTTP. What the panel watches is the code the tests verified.
  • This is the same split etcd's Raft library uses: the library implements the algorithm, and the caller does network and disk I/O.

4 · The Raft core raft/

This is the part to own line by line. Everything else exists to drive it or to show what it's doing.

class RaftNode:
    def __init__(self, node_id: str, peers: list[str], storage: Storage,
                 rng: random.Random, config: RaftConfig): ...

    # inputs
    def tick(self) -> None                        # advance logical time by one tick
    def receive(self, msg: Message) -> None       # handle one incoming Raft message
    def propose(self, command: dict) -> tuple[int, int] | None
                                                  # leader: append, return (index, term); else None
    # outputs, drained by whichever driver is running the node
    def take_messages(self) -> list[Message]      # messages to send
    def take_committed(self) -> list[Entry]       # newly committed entries, in log order

    # read-only, for drivers, the dashboard and invariant checks
    role, term, leader_id, commit_index, log, events

@dataclass
class RaftConfig:
    heartbeat_interval: int = 10                  # ticks
    election_timeout: tuple[int, int] = (30, 60)  # random in [lo, hi) ticks

At 100 ms per tick that's a heartbeat every 1 s and elections after 3–6 s, slow enough to watch. The tests use the same numbers, since ticks cost nothing there.

How take_messages() and take_committed() work

The node never sends anything or applies anything itself. While it handles an input, it only writes down what should happen next, in two places:

  • An outbox: a list of messages it wants to send, such as a vote reply or heartbeats.
  • Committed-but-not-applied entries: everything between last_applied + 1 and commit_index.

"Take" means hand over once.

  • take_messages() returns the outbox and empties it.
  • take_committed() returns the newly committed entries in log order and moves last_applied forward, so each entry is handed out exactly once.

Example: a follower receives an AppendEntries carrying entry 7, with leader_commit = 7. It appends and saves the entry, queues a "success" reply, and moves its commit index from 6 to 7. Then take_messages() returns [reply to leader] and take_committed() returns [entry 7].

Can multiple threads interfere with these steps?

No, because no threads touch the node. The simulator is a plain loop. The demo server runs a single asyncio event loop, which is one thread. Asyncio only switches between tasks at an await. The node's methods are ordinary functions with no await inside. So calling the node and collecting its outputs always runs start to finish, with nothing in between.

All three entry points (the POST /raft handler, the tick loop and POST /client/write) go through one helper:

def step(self, call):
    result = call()                          # node.receive / tick / propose: plain function, no await
    for m in self.node.take_messages():
        asyncio.create_task(self.post(m))    # sends run later as their own tasks and never touch the node
    for e in self.node.take_committed():
        self.apply(e)                        # update the KV store, wake any waiting client write
    return result

# for example, inside the POST /raft handler:
self.step(lambda: self.node.receive(msg))

There's one rule: never put an await between calling the node and collecting its outputs. With one helper, that rule lives in one place. This is also why the design uses asyncio. A threaded web server would need a lock around the node.

Is the outbox more complicated than calling send() directly?

A · Outboxcurrent / recommended
self.outbox.append(reply)   # inside the node
# the driver collects it after the call returns
  • ✅ Messages can't leave before the handler has finished saving term, vote and log. R1 is guaranteed by the structure.
  • ✅ The node holds no reference to the network. A unit test calls receive() and inspects take_messages().
  • ➖ About 5 extra lines in the node, plus the step() helper in each driver.
B · Callbacks
RaftNode(..., send=transport.send, apply=kv.apply)
self.send(reply)            # inside the node
  • ✅ Reads exactly like the paper.
  • ➖ R1 becomes a habit, not a guarantee. Every handler must save before calling send(), which is easy to break in a later edit, by you or an AI.
  • ➖ It doesn't remove the one-thread requirement. The same rule about await applies.

Recommendation: keep the outbox. The two are about the same size, and the outbox turns R1 from a rule we have to remember into one we can't break. You can choose in Q10.

Correction to draft 2: I said callbacks could let the simulator deliver a message into the node mid-handler. Our simulator always queues messages with a delay, so that can't happen here. I've removed that argument.

In plain words: node3, the leader of term 4, tells node1: "Your log should already have entry 6, with term 4. If it does, put this new entry after it as entry 7. Entries up to 6 are committed."

KeyWhat it meansIn this example
typeWhich of the four message kinds this is. The receiver uses it to pick the handler.AppendEntries
src, dstSender and receiver node IDs. Every message carries both, so a reply knows where to go and a partition filter knows what to drop.node3 → node1
termThe sender's current term. If it's lower than the receiver's, the receiver rejects the message (the sender is a stale leader). If it's higher, the receiver adopts that term and becomes a follower (R2).node3 is the leader of term 4
prev_log_indexThe index of the entry just before the new ones.6
prev_log_termThe term of that entry, according to the leader's log.4
These two together are the consistency check. The follower accepts the entries only if its own entry at prev_log_index has term prev_log_term. If it doesn't, it replies with failure and the leader retries starting further back. This is what keeps every log identical."Does your entry 6 have term 4?"
entriesThe new entries, each with the term it was created in and the command. There's no index field: an entry's position is prev_log_index + 1, then + 2, and so on. An empty list makes this a heartbeat.One entry, which becomes #7: set z = 7, created in term 4
leader_commitThe highest index the leader knows is committed. The follower moves its own commit index up to min(leader_commit, index of its last new entry), which is how followers find out what's safe to apply.Entries 1–6 are committed. 7 isn't yet, since it was just sent.

Replies describe themselves. Messages are one-way (Q4), so the leader can't look up "which request was this a reply to?" Each reply carries everything needed to handle it, in any order. The leader ignores stale replies: ones with a lower term, or a match_index below what it already knows.

R7A new leader appends a no-op entry in its term, so entries from earlier terms get committed without waiting for a client write.test_new_leader_commits_previous_entries

State machine

Commands are {"op": "set", key, value}, {"op": "delete", key} and {"op": "noop"}. Every node applies them in log order. After a restart, the KV store is rebuilt by re-applying committed entries from index 1, since there are no snapshots. The log starts at index 1; index 0 is a placeholder entry with term 0.

5 · The simulator sim/

SimNetwork(rng, drop, dup, delay)

  • Each message gets a random delay of 1–N ticks, so messages get reordered without any extra work.
  • Random drop and duplicate rates.
  • partition(groups) / heal(): messages between groups are dropped.

SimCluster(n=5, seed)

  • step(): tick every live node, deliver messages that are due, collect outboxes, apply committed entries, check invariants.
  • crash(i) throws away the node object but keeps its MemoryStorage, which plays the role of the disk. restart(i) rebuilds the node from that storage.
  • Helpers: run_until(cond, max_ticks), leader(), write(key, value).

6 · The node runtime server/

  • Every call into RaftNode happens on the one event loop, so no locks are needed.
  • After every input (a tick, a message, or a write), flush() runs: it sends take_messages() over HTTP (fire-and-forget, 500 ms timeout, errors ignored, since Raft already tolerates lost messages), applies take_committed() to the KV store, and resolves pending writes.
  • Partition filter: each node keeps a set of blocked peers and drops messages going to or coming from them. Control endpoints (/state, /admin, /client) aren't filtered.
  • Storage: in memory for tests, one file for the demo. See below.

Storage: do we need a file?

Tests: no file

MemoryStorage is a plain Python object. When the simulator "crashes" a node, it throws the node away but keeps this object, just as a real disk would survive. It's fast, and no files are involved.

Docker demo: yes, one file

Killing a container wipes its memory. Without a file, a restarted node comes back with term 0, no record of its vote, and an empty log.

What goes wrong if the demo has no file:

  1. It can vote twice in the same term. It forgets it already voted, so two candidates can both win the same term and you get two leaders (breaks Election Safety).
  2. It forgets entries it acknowledged. The leader counted that acknowledgement toward a majority. If enough nodes forget, a committed write disappears.

This is rule R1, and "what happens when a node restarts?" is very likely a panel question. With one crash at a time the demo would probably look fine, but it wouldn't be correct Raft.

Kept simple, as you asked: one file and an fsync on every change. This is the whole implementation:

def _save(self) -> None:              # called on every change to term, vote or log
    tmp = self.path + ".tmp"
    with open(tmp, "w") as f:
        json.dump({"term": self.term, "voted_for": self.voted_for, "log": self.log}, f)
        f.flush()
        os.fsync(f.fileno())             # on disk before we return
    os.replace(tmp, self.path)           # swap in: the file is always old or new, never half-written
One concern, so I kept two extra lines: if we write straight over raft.json and the node is killed mid-write, it's left with half a JSON file and can't start again. Writing to a temp file and swapping it in costs two lines and removes that problem. Everything else (append-only logs, directory fsync, checksums) is left out on purpose.

Side note for the panel: a killed container's writes are already in the operating system's cache, so in this demo fsync only matters if the whole machine loses power. We do it anyway because it's one line and it's what Raft requires. If you'd still rather have no file, the only consistent alternative is Q2's "crash endpoint inside the app", which keeps memory alive inside the process. That means no real crash.

How a client write works (3-node example)

The leader replies only after the entry is applied. If index 7 ends up applied with a different term (it was overwritten), or the node loses leadership, the client gets 503. If nothing is committed within 5 s it gets 504. A client never sees "ok" for a write that could still be lost.

7 · Docker setup and dashboard

docker-compose.yml

  • One image (python:3.12-slim + aiohttp) for all 6 containers. Only the start command differs.
  • node1–node5: fixed container names, with NODE_ID, PEERS and TICK_MS=100 set as environment variables. Each has its own named volume at /data, and restart: "no" so a killed node stays down until you start it.
  • dashboard: port 8080, with /var/run/docker.sock mounted (Q2).
  • docker compose down -v wipes all state between demo runs.

Dashboard API

  • GET /api/cluster: sends GET /state to every node (300 ms timeout). No answer means the node is down.
  • POST /api/write: sends to the current leader and follows a 421 to the real one.
  • POST /api/partition: takes {groups} and works out each node's blocked set.
  • POST /api/heal
  • POST /api/nodes/{id}/kill, /start: the Docker Engine API. Kill sends SIGKILL, so it's a real crash with no graceful shutdown.

8 · Demo scenarios

1 · The leader fails

  1. Kill the leader.
  2. After 3–6 s, a follower becomes a candidate and wins at term + 1.
  3. A write succeeds on the new leader.
  4. Start the old leader. It rejoins as a follower and its log catches up.

point out the term number goes up, and committed entries survived.

2 · A follower fails and catches up

  1. Kill node4.
  2. Write 5 values. They commit with 4 of 5 nodes.
  3. Start node4. Its log fills in and its KV store matches the others.

point out node4 kept its term and log on disk, and the leader works backwards to find where their logs match.

3 · Partition with the leader in the minority strongest

  1. Apply "leader + 1 | rest".
  2. Write to the old leader. The entry stays dashed and the request returns 504.
  3. The majority side elects a new leader, and writes there commit.
  4. Heal. The old leader steps down and its uncommitted entries are replaced.

point out there are never two leaders making progress at once, and only uncommitted entries are ever lost.

4 · No majority

  1. Kill 3 of the 5 nodes.
  2. The 2 survivors keep running elections and the term keeps climbing, but there's no leader and writes fail.
  3. Start one node. A leader is elected and writes work again.

point out Raft gives up availability to stay consistent. The climbing term leads into a discussion of pre-vote.

9 · Test plan

The tests are the evidence of correctness. The demo only illustrates. Every test runs on the simulator, so none of them need Docker or a real clock.

FileCases
test_election.pyExactly one leader is elected · re-election after the leader crashes · split votes resolve · a candidate with an outdated log can't win (R3) · a restarted node doesn't vote twice in a term (R1) · followers don't start elections while a leader is healthy (R4)
test_replication.pyA write commits and is applied on all nodes · a lagging follower catches up · conflicting uncommitted entries get overwritten · reordered or duplicated AppendEntries don't truncate the log (R5) · a new leader commits earlier-term entries via its no-op (R7)
test_failures.pyA leader in the minority can't commit · after healing it steps down and its entries are overwritten (R2) · with no majority there's no leader and no commits · restoring one node brings progress back · the Figure 8 scenario, scripted step by step (R6)
test_fuzz.pyMany seeds, each with a random schedule of crashes, restarts, partitions and heals, plus dropped, duplicated and delayed messages, and random client writes. Invariants are checked every tick. At the end everything is healed and the run must show progress: a leader emerges, every acknowledged write is present, and all KV stores are equal. The seed count can be raised with an environment variable for long runs.
test_units.pyMessage JSON round-trips · KV apply · log helpers

Invariants (tests/invariants.py, checked after every simulator step)

InvariantCheck
Election SafetyAt most one leader per term, ever. The checker keeps a record of term → leader.
Log MatchingIf two logs have the same (index, term), they're identical up to that index.
Leader CompletenessEvery entry ever committed is in the log of every later leader.

12 · Risks and trade-offs

Risk or trade-offWhy it mattersMitigation / how I'd explain it
Demo work eats the dayThe brief values small, well-tested workBuild it last, cap it at about 2 h, tests first
Docker isn't installed hereThe demo can't runInstall Docker Desktop or OrbStack before step 6. The tests never need it.
Partitions are simulated in the appReal network failure isn't exercisedSay so openly. The core can't tell the difference. iptables would be the next step.
docker.sock is mounted into the dashboardIt gives root-level access to Docker on the hostLocal demo only, and documented. Alternatives are in Q2.
The real runtime isn't deterministicDemo runs can't be reproducedThe seeded tests are the evidence; the demo only illustrates.
FileStorage rewrites the whole fileEach write costs time proportional to the log sizeFine at demo scale. The real fix is an append-only log file.
No snapshotsThe log grows forever, and a restart replays all of itOut of scope. A natural topic if they ask to extend the design live.
Term inflation without pre-voteA node rejoining with a high term can depose a healthy leaderVisible in scenario 4. Pre-vote is the extension.
AI-written Raft logic has subtle bugsFigure 8, truncation and timer resets are the classic onesEach rule (R1–R7) has a named test, plus the fuzz test. Bugs caught get logged in AI_NOTES.md.

13 · Out of scope (listed in the README as trade-offs)

Snapshots / log compaction Adding or removing nodes Pre-vote and check-quorum Linearizable reads (ReadIndex / leases) Real network faults (iptables / tc) Auth / TLS Performance tuning

There's no client read API. The dashboard reads each node's local state directly, which is exactly what makes nodes disagreeing visible.
